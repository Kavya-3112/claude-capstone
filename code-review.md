## Findings (verified by code reading unless marked)

### HIGH
**CR-01. Retry of "Replace" after a failed contacts write is blocked by the tool's own backup.**
- `src/storage/repository.ts:176-177` and `:186-198`; `src/state/store.ts:304`.
- Behaviour: `replaceUnreadable` writes `BACKUP_KEY` (line 186), then writes the new envelope (195). If step 4 fails (quota), it returns `writeFailed` with `backupKept: true` and leaves the backup in place. A second `replaceUnreadable` call hits `checkLeftoverBackup()` at line 176, finds that backup, and returns `leftoverBackupPending`.
- Scenario: corrupt data, storage nearly full. User clicks Replace, the write fails with quota, user frees space and clicks Replace again. They get `leftoverBackupPending`. The store never sets `state.leftoverBackup` (it only does so in `init`/`reload`), so the UI has no prompt to show, and it cannot tell the user why. The user is stuck until they reload the page, and the reload then offers "restore", which writes the corrupt raw value back over the original (a loop). `tests/unit/repository.test.ts:217` and `store.test.ts:224` assert the first failure only and never retry.
- Fix: track backups created by this session (for example `backupWrittenThisSession`) and skip the leftover refusal for them, or reuse the existing backup if it equals `raw`. Add a retry test at repo and store level. Also have `store.replaceUnreadable` surface `leftoverBackupPending` into state.

### MEDIUM
**CR-02. Restoring a leftover backup overwrites the contacts key with no stale check or validation.**
- `src/storage/repository.ts:153-163`.
- Scenario: a backup was left after a failed removal. Later the user adds contacts in this or another tab. On next startup "Restore" writes the old backup over the newer valid data. Unlike `save` (line 123) and `replaceUnreadable` (182), there is no comparison against the current raw value and no check that the backup parses. Decision 6 says restore writes raw to the contacts key but does not say it may clobber newer data. Silent data loss.
- Fix: compare the current value first, and show the user what will be replaced (or refuse when the current value is valid and differs). Add a test with a valid, newer contacts value.

**CR-03. A throwing subscriber prevents persistence.**
- `src/state/store.ts:108-111, 211-212, 223-224, 231-235`.
- `set()` calls listeners synchronously with no try/catch. In `addContact` the in-memory change is applied through `set()` before `persist()`. If any listener throws (UI render bug), `persist()` is never called and the exception propagates. The contact is displayed but never saved, and `saveStatus` still says `saved`. This violates the "change applied then persisted, never silently unsaved" intent (architecture section 6).
- Fix: persist first-class, e.g. compute new state, persist, then notify; or wrap listener calls in try/catch. Add a test with a throwing listener.

**CR-04. No CSP is present yet and no test enforces rendering safety.**
- `index.html` (head has no CSP meta); `impl-plan.md:264-271` assigns it to T-24.
- Not a defect against T-13's scope, but the whole UI (T-14 onward) will be built before any CSP exists, and `index.html` loads `/src/main.ts` and an external stylesheet only (no inline scripts), so a `default-src 'self'` meta CSP can be added now at no cost. Note the dev server (Vite) injects inline scripts, so the CSP must apply to the build only. Rated MEDIUM because of NFR-09 and the XSS name test being deferred.
- Fix: add the meta CSP to the build output early, and add the grep check for `innerHTML` in T-14 rather than T-24.

**CR-05. Stale-write check is not atomic; the residual window is undocumented.**
- `src/storage/repository.ts:118-126`.
- `get` then `set` on localStorage can interleave with another tab between the two calls. The check reduces but does not remove lost updates. This is an inherent limit of localStorage, but the architecture claims a stale check (FR-57) without stating the window.
- Fix: document the limitation in architecture/README, and keep the `storage` event handling (T-21) as the second layer.

### LOW
**CR-06. `createdSeq`/`nextSeq` accept unsafe integers.** `src/storage/schema.ts:44-46` uses `Number.isInteger`. A stored `createdSeq` of 1e300 passes, then `nextSeq + 1` (ordering.ts:23) equals itself, so a new contact collides with an existing `createdSeq` and ordering becomes ambiguous. Use `Number.isSafeInteger`. Add a test.

**CR-07. Unknown fields in stored records and envelope are dropped on the next save.** `schema.ts:61` rebuilds records with five fields only, so data written by a newer app version loses extra fields. Acceptable for version 1, but there is no forward-compatibility note; the `version !== 1` check already makes newer versions unreadable.

**CR-08. `restoreLeftoverBackup` leaves repository state `unloaded`** (`repository.ts:160`) until the caller reloads. `save` only blocks on `unreadable`, so a save before `load()` is allowed against a baseline that does not match in-memory data. The store does reload, so no current caller triggers it. Consider blocking `save` in the `unloaded` state.

**CR-09. Live regions: `role="alert"` plus `aria-live="assertive"` plus `aria-atomic`** (`index.html` live-assertive). The redundant attributes can cause double announcements in some screen reader and browser pairs. Not verified with any assistive technology. Keep one mechanism and test with the screen readers decided under Q-08.

- `tests/unit/store.test.ts` has no case for `init()` when the backup check itself fails (`checkLeftoverBackup` returns `unavailable`, repository.ts:136, which `store.init` treats as "no backup").

## Findings

### HIGH
**CR-12. The controls-disabled-with-a-visible-reason fix from decision 18 (item 4) is not implemented; blocked Add/Edit/Delete controls stay fully enabled with only a transient alert.**
- `impl-plan.md` decision 18: "...blocked Edit/Delete/Add controls must be disabled with a visible reason, settling the earlier open question..." This is a specific, recorded commitment, distinct from the earlier "open question" it says it settles.
- `src/state/store.ts:138-147` exposes `mutationBlock()` / `blocked()` (`'recovery' | 'leftover-backup' | 'stale' | null`), clearly built so the UI could consult it to disable controls.
- `grep -n "mutationBlock|disabled" src/ui/*.ts src/state/store.ts` finds exactly one `disabled` usage anywhere in the UI layer: the own-copy checkbox gating in `src/ui/recovery.ts:217-220` (`backup-failed` step). `mutationBlock()` is defined but never called from any UI module (`list.ts`, `form.ts`, `main.ts`, `search.ts`, `banner.ts`).
- `src/ui/messages.ts:27-29` defines `blockedRecovery`, `blockedLeftover`, `blockedStale` ("Add, edit and delete are turned off until you... (see above)."), and `finishEditFirst` at line 26. `grep -rn "blockedRecovery|blockedLeftover|blockedStale|finishEditFirst" src tests` finds these four strings only in their own definitions — they are never read anywhere in `src/` or asserted in `tests/`. This is dead code that looks like exactly the "visible reason" text the decision asked for, drafted but never wired to any element.
- Instead, `src/ui/list.ts:72-74,92-94,116-119,163-164` and `src/main.ts:62-64` all call a generic `reportBlocked()` / `announcer.alert(MSG.blocked)` ("Changes cannot be made right now.") only *after* the user has already clicked Add, Edit or Delete and the store returned `{ ok: false, blocked: ... }`. The buttons themselves carry no `disabled`, `aria-disabled`, or visible explanatory text beforehand.
- Confirmed by execution, not just reading: `tests/e2e/recovery.spec.ts:64-79` ("add, edit and delete are blocked; search still works; nothing is written") clicks `Add contact`, `Edit Bob`, `Delete Bob` then `Delete contact` while in `recovery-needed` state — all these clicks succeed as clicks (Playwright's `.click()` would time out/fail on a genuinely `disabled` button), and the test only asserts the resulting alert text and that nothing changed, never that any control was disabled. This test passed in the run above, which is consistent with the controls being enabled, not consistent with them being disabled.
- Impact: a screen-reader or keyboard user gets no advance indication that the page is in a non-editable state until after acting on a control and receiving a generic, non-specific alert ("Changes cannot be made right now." — it does not say *why*, unlike the drafted `blockedRecovery`/`blockedLeftover`/`blockedStale` strings that would have). This also means the T-14, T-18 and T-20 status notes in `impl-plan.md`, which report these tasks as implemented without flagging this gap, do not disclose that a specific, recorded decision item was left undone.
- Recommendation: wire `store.mutationBlock()` into `list.ts` (Edit/Delete buttons), `main.ts`/`form.ts` (Add submit), and `search.ts` is correctly exempted (decision 7, read-only); set `disabled` plus a visible reason near the controls (the drafted `blockedRecovery`/`blockedLeftover`/`blockedStale` strings, or similar) instead of relying solely on a post-click alert; add a test asserting the disabled state and the visible reason text, as decision 18 itself requires ("Each fix gets a test").

### MEDIUM
**CR-13. The interaction between a pending (unconfirmed) replacement backup in one tab and another tab's "foreign leftover backup" detection is untested and was only checked by manual trace, not by an executed test.**
- `src/storage/repository.ts:80, 169-174, 222-264` tracks `ownBackupRaw` per `ContactRepository` *instance* so a tab does not mistake its own in-flight replacement backup for a leftover (CR-01 fix). `src/ui/tabs.ts:17-18,21-22` makes every other tab call `store.refreshLeftoverBackup()` → `repo.foreignLeftoverBackup()` on any `storage` event or focus/visibility recheck for the backup key, and a different tab's `ContactRepository` instance has its own, unrelated `ownBackupRaw` (null), so it will report the first tab's own, not-yet-confirmed backup as a genuine "leftover" and show the leftover-restore/discard panel to its user (`src/ui/recovery.ts:108-136`).
- By reading the code I traced a scenario where Tab A replaces unreadable data (backup kept, awaiting confirmation) and Tab B, which had independently loaded the same originally-corrupt data, sees the backup key appear, is shown "A backup was found," and if its user clicks "Restore backup" and then confirms "Restore anyway" past the changed-data warning (CR-02/decision 10's `needsConfirmation` path), Tab B will write the pre-replacement raw corrupt value back over Tab A's now-valid data. Tab A should then detect this via its own `storage`-event staleness watch (`watchOtherTabs` → `checkStale()`) and be blocked from confirming further writes until it reloads — which on reload would show the recovery screen again for the same corrupt data. I did not execute this scenario; it is a read-only trace, not a confirmed defect, and no CRITICAL is claimed.
- `grep -n "ownBackupRaw|foreignLeftoverBackup|refreshLeftoverBackup" -r src tests` finds no unit test of `foreignLeftoverBackup()` directly, and `tests/e2e/tabs.spec.ts` (T-21) and `tests/e2e/recovery.spec.ts` (T-20) have no test that combines a pending backup-then-replace in one tab with a second tab open and watching the backup key — the two task's e2e suites each test their own feature in isolation.
- Recommendation: add at least one two-tab Playwright test that starts a replace in tab A (backup kept, unconfirmed) and opens tab B to check what tab B is shown, and whether tab A is correctly warned/blocked if tab B acts on the backup before tab A confirms. Until that exists, this interaction is an open question, not a verified-correct behaviour.

### New finding: CR-17 (LOW) — confirmDialog's delete-confirmation button is not reactively disabled if a block newly appears while the dialog is already open

- **Severity:** LOW.
- **Affected files:** `src/ui/confirmDialog.ts` (the whole module — `showChoiceDialog`/`confirmDelete` build a static, one-shot `<dialog>` with no subscription to the store), `src/ui/list.ts:103-122` (`startDelete`, which opens the dialog and, on confirm, calls `store.deleteContact` and only then checks `mutationBlock`-derived rejection via `reportBlocked()`).
- **Behavior/risk:** If a mutation block (recovery, leftover-backup, or stale) appears *after* a user has opened the delete-confirmation dialog for a row but *before* they click the dialog's action button, the dialog's "Delete contact" button stays enabled and shows no reason text — `showChoiceDialog` builds the dialog once, synchronously, with no `store.subscribe` hook to update it. Clicking it then calls `store.deleteContact(contact.id)`, which correctly refuses the mutation (confirmed by reading `store.ts`'s `blocked()` check inside `deleteContact`), and `list.ts`'s `startDelete.onConfirm` falls back to the pre-existing generic `reportBlocked()` → `announcer.alert(MSG.blocked)` ("Changes cannot be made right now.") instead of the specific, newly-wired reason text. No data corruption or incorrect deletion occurs — the store-level guard still holds — but the user experience regresses to exactly the pre-CR-12 behaviour (generic, after-the-fact alert, no advance/visible reason) for this one narrow timing window.
- **Evidence:** `src/ui/confirmDialog.ts` in full (read above) has no `store` reference at all. `src/ui/list.ts:103-122`'s `startDelete` confirms the fallback path (`else { reportBlocked(); focusPlanTo(...); }`). `grep`-ing `tests/e2e` for a test that opens the delete dialog and then introduces a block before confirming found none; this path is untested.
- **Disposition:** this is a genuine, if narrow, gap against decision 18 item 4's wording ("blocked Edit/Delete/Add controls must be disabled with a visible reason") — the delete dialog's action button is itself an Edit/Delete-adjacent control that is not disabled in this specific race — so it is logged as a new, separate finding (CR-17) rather than folded into the CR-12 resolution or silently accepted as a documented limitation. It is LOW rather than HIGH/MEDIUM because: (a) it requires a precise timing window that did not occur in any of the three full e2e runs performed in this re-review; (b) the store-level block still prevents the actual mutation; (c) a safe, specific fallback already exists via decision 7's/CR-03's generic alert path. Whether to fix this now or accept it as an additional residual risk (alongside CR-13/CR-05) is for the orchestrator/user to decide; this review takes no position beyond logging it.
- **Suggested fix (not implemented by this review):** either have `confirmDelete`/`showChoiceDialog` subscribe to `store.mutationBlock()` while open and disable/relabel the action button reactively, or re-check `mutationBlock()` immediately before calling `onConfirm` and show the specific `blockedReasonText` in the dialog itself (not just the generic alert) if a block appeared after open.
